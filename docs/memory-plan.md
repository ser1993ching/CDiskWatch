# 内存审计与瘦身方案（P0/P1 已实施）

> 测量环境：Windows 11 / .NET 8 / 发布版单文件（`publish/win-x64/CDiskWatch.exe`，12.3 MB）/ 96 DPI /
> 面板 1180×780 / 本机 C 盘 696,207 个文件、14,753 个分区键、当前 12 份历史快照。
> 复现脚本：`tools/memprobe.ps1`（分阶段采样 + 句柄峰值）、`tools/wsprobe.ps1`（验证 EmptyWorkingSet 效果）。

---

## 一、现状测量

| 场景 | 工作集 WS | 私有内存(提交) | 句柄 | GDI/USER |
|---|---|---|---|---|
| 托盘空闲（面板未打开） | **38.2 MB** | **16.9 MB** | 253 | 46 / 22 |
| 面板打开（概览页） | 46.2 MB | 18.7 MB | 335 | 46 / 22 |
| 打开过「历史」页 | 59.9 MB | **31.2 MB** | 337 | 49 / 22 |
| 扫描中峰值 | **110.9 MB** | **80.1 MB** | **59,596** | 52 / 25 |
| 扫描结束后常驻 | **113.4 MB** | **82.8 MB** | 2,073 | 50 / 25 |

参考：同机 `WizTree`/`TreeSize` 全盘扫描时通常 150~400 MB；本项目目标一直是「托盘常驻 < 40 MB」。

**关键结论：真正的问题不在「平时」，而在「扫描后」——一次扫描会把进程永久撑到 ~83 MB 私有内存、~113 MB 工作集。**
而这 83 MB 里 **真正活着的数据只有约 4 MB**（GC 堆），其余是「扫描期间堆膨胀后没有归还给系统」的已提交内存。

对照实验（控制台里跑同一条扫描代码路径，逐步回收）：

| 步骤 | GC 堆 | 私有内存 | 工作集 | 已提交 |
|---|---|---|---|---|
| 进程启动 | 0 MB | 7 MB | 23 MB | 1 MB |
| 扫描结束 + 普通 compacting GC（**现在的做法**） | 4 MB | **30 MB** | 49 MB | 24 MB |
| 再加 `Aggressive` GC + LOH 压缩 | 4 MB | **10 MB** | 29 MB | 4 MB |
| 健康检查：载入 Latest+Prev 两份快照 | 4 MB | 28 MB | 49 MB | 20 MB |

→ **只把「拼命的 GC」换成「会归还内存的 GC」，私有内存立刻从 30 MB 掉到 10 MB**（这一项就有 −20 MB）。

## 二、内存都花在哪（逐项实测）

| 组成 | 实测占用 | 说明 |
|---|---|---|
| .NET 运行时基线 | 私有 7 MB / WS 23 MB | JIT、GC、线程栈、CLR 自身，已开 `ConserveMemory=9`、`RetainVM=false`、`InvariantGlobalization` |
| UI 与窗口（首次绘制后） | 私有 +11.5 MB | 字体、GDI 对象、窗口、双缓冲位图（**每帧新建 3.5 MB 兼容位图**，见 P1-6） |
| 每份快照（`Snapshot`） | **约 1.3 MB GC 堆** | 3,711 个目录条目 + 600 条祖先汇总 + 100 大文件 + 23 条建议（12 份快照实测 +13 MB） |
| Latest + Prev + Baseline 常驻 | ~3.9 MB | `Monitor.RefreshDerived` 每轮从磁盘重载这 3 份 |
| 历史页快照缓存 | **+12.5 MB（本机 12 份）** | `Monitor._historyCache` 缓存**完整快照**，且**永不释放**；历史仓库上限 300 MB，按 117 KB/份可到 ~2500 份 → 最坏会涨到 **~3 GB** |
| 扫描期临时内存 | 峰值 +23~50 MB | 分区键字典（14,753 条字符串+对象）、建议引擎递归产生的垃圾 |
| 建议引擎垃圾 | +约 20 MB 峰值 | `FileSystemEnumerable` 递归测量 WinSxS/Docker 等 26 条规则，10 MB 垃圾 + 8 秒耗时 |
| 句柄峰值 | **59,596** | 全部来自 `FileSystemEnumerable` 递归（对照：原生 `FindFirstFile` 递归峰值 **211**） |

**顺带发现的三个 Bug（与内存/资源直接相关，已定位）：**
1. 建议测量用 `FileSystemEnumerable` 递归，句柄峰值 ~6 万（框架枚举器 + 安全检查在递归结束时才集中释放）。原生递归同样 18,420 MB 结果、同样 ~8 秒，但句柄只有 211。
2. `PaintTo` 每帧 `CreateCompatibleBitmap(1180×780)` = 3.5 MB，鼠标悬停每动一下就重绘一次。
3. 历史页缓存的是完整快照而不是趋势所需的三元组。

## 三、方案清单（按收益/风险排序）

### P0-1 扫描后用「会归还内存」的 GC（3 行，最低风险）

```csharp
// Monitor.RunScan 线程末尾，替换现有的两次普通 compacting GC
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect(2, GCCollectionMode.Aggressive, blocking: true, compacting: true);
GC.WaitForPendingFinalizers();
GC.Collect(2, GCCollectionMode.Aggressive, blocking: true, compacting: true);
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.Default;
```

**实测：私有 30 → 10 MB，WS 49 → 29 MB，已提交 24 → 4 MB。**
估算收益：扫描后 **−20 MB 私有 / −20 MB WS**，代价是扫描结束多花 ~50 ms。

### P0-2 历史页只缓存「趋势/列表需要的轻量头」（半天）

新增 `Snapshot.ReadHeader(path)`：只读到类别数组为止（约 200 字节），返回 `{Time, Total, Free, Used, UsedRatio, FileCount, DirCount}`。
`Monitor.History()` 改为返回 `List<SnapHeader>`；历史页折线图与表格都用它；「概览」仍用完整快照。

**实测：现在 +12.5 MB（12 份）；改完 ≈ +2 KB，并且不再随快照数量线性增长。**
估算收益：**−12.5 MB（本机）**，长期稳定（否则 1 年后可能 +450 MB）。风险低（快照格式不变，只多一个只读解析入口）。

### P0-3 扫描后/隐藏到托盘时把工作集还给系统（10 行）

* 扫描结束、`WM_CLOSE`（隐藏到托盘）后各调用一次 `SetProcessWorkingSetSize(GetCurrentProcess(), -1, -1)`。
* 不做定时调用（避免打断用户操作时的响应）。

**实测：面板打开时 WS 46.2 → 5.3 MB（6 秒后 7.4 MB，私有同时从 18.7 降到 13.6）。**
估算收益：**WS −30~40 MB（观感最明显的一项）**；代价是下次交互时缺页（见下方实测）。
注意：这只降「工作集」，**不降私有内存**，所以它必须和 P0-1 一起做才有意义。

**trim 后「回来」的实测代价**（隐藏 → trim → 重新显示并强制重绘一次）：

| 处理 | 工作集变化 | 重绘期间缺页数 | 重绘 CPU 时间 |
|---|---|---|---|
| 不 trim | 49.5 → 49.6 MB | +23 ~ +35 | ~31 ms |
| trim | 4.5 → 13.5 MB | **+816 ~ +2316** | 15 ~ 62 ms（与不 trim 同量级，属计时器粒度噪声） |
| trim | 7.2 → 10.4 MB | +816 | 62.5 ms |
| 不 trim | 52.5 → 52.6 MB | +35 | 31.3 ms |

结论：**多出来的只有 800~2300 次软缺页（页还在物理内存里，微秒级），没有测到额外的 CPU 开销**；
DWM 会保留隐藏前的最后一帧，所以重新显示时不会白屏/闪烁。只有在机械盘、
或系统内存吃紧导致这些页真被写进 pagefile（变成硬缺页）时，才会有一次 100~300 ms 的卡顿。

### P1-4 建议引擎改用原生递归（半天）

把 `AdviceEngine.MeasureDir` 换成与 `Scanner` 同款的原生 `FindFirstFile/FindNextFile` 递归（跳过联接点、复用缓冲区）。

**实测：结果一致（18,420 MB），耗时一致（磁盘瓶颈 ~8 s），句柄峰值 59,596 → 211，垃圾 −~10 MB。**
估算收益：**句柄峰值 −99%（6 万 → 200）+ 扫描峰值私有 −10~17 MB**；同时消掉「任务管理器里句柄数吓人」的观感问题。

### P1-5 Baseline 懒加载（3 行）

`Monitor.RefreshDerived` 不再预加载 `Baseline`（UI 从不使用它，只有 `--report --baseline` 才需要）。
估算收益：**−1.3 MB 常驻**。

### P1-6 扫描结束复用内存里的新快照（10 行）

现在 `Store.Save(snap)` 之后 `RefreshDerived` 又**从磁盘重新读 3 份**快照。改成：新快照直接作为 `Latest`，原 `Latest` 降级为 `Prev`。
估算收益：**省 2 次反序列化（~2 MB 临时对象）**，扫描后 `RefreshDerived` 快 ~100 ms。

### P1-7 双缓冲位图缓存（10 行）

`PaintTo` 里缓存 `{w,h}` 对应的兼容位图/DC，窗口尺寸变化时才重建。
估算收益：每帧少 3.5 MB 分配（悬停重绘时尤其明显），GDI 峰值更稳。

### P2-8（可选）用扫描数据替代 WinSxS 的精确测量

`C:\Windows\WinSxS` 在扫描结果里就是第 2 级目录，其大小已由祖先汇总算出。规则命中「聚合深度以内的路径」时直接取扫描数据，不再递归。
估算收益：**扫描总耗时 −8 秒（12.6 s → 约 4.6 s）**，内存影响小（属于性能优化）。风险：路径在深度 4 以下时仍回落递归，需要写清判定条件。

### P3-9（后续实验）NativeAOT

发布改成 AOT 后运行时基线可再降 30~50%（私有 7 → 3~4 MB），单文件更小。
风险：GDI/P-Invoke、`System.Text.Json` 源生成、反射都用到了，需要单独验证；不建议和本轮一起做。

## 四、预期效果（估算）

| 场景 | 现在（WS / 私有 / 句柄） | 做完 P0 | 做完 P0+P1 | 说明 |
|---|---|---|---|---|
| 托盘空闲 | 38 / 17 / 253 | ~22 / ~12 / 253 | **~20 / ~11 / 253** | 基线 + Latest/Prev |
| 面板打开 | 46 / 19 / 335 | ~28 / ~13 / 335 | **~26 / ~13 / 335** | 有交互后会重新缺页增长 |
| 打开过「历史」页 | 60 / **31** / 337 | ~28 / ~13 / 337 | **~26 / ~13 / 337** | 不再缓存完整快照 |
| 扫描中峰值 | 111 / **80** / **59.6k** | ~70 / ~50 / ~350 | **~60 / ~45 / ~350** | 建议引擎改原生后 |
| 扫描结束后 | **113 / 83** / 2,073 | ~15 / ~12 / ~350 | **~12 / ~11 / ~350** | Aggressive GC + 归还工作集 |
| 历史仓库 1 年后（365 份） | +470 MB（会 OOM） | +2 KB | **+2 KB** | 轻量头方案 |

**总体评估**

* **扫描后的常驻内存：83 MB → 约 11~13 MB（−85%）**，工作集 113 MB → 12~15 MB（−88%）。
* **日常托盘空闲：17 MB → 约 11 MB（−35%）**，工作集 38 MB → 20 MB（−47%）。
* **句柄峰值：59,596 → 约 350（−99%）**。
* 代价：一处 50 ms 的额外 GC、隐藏到托盘后首次打开面板时轻微缺页、半天左右的重构工作量。
* 风险最高的是 P1-4（改原生递归，但已有 `Scanner` 的成熟实现可以直接复用）与 P2-8（判定条件写错会算错建议值，建议先只对 `Level <= MaxDirLevel` 的路径启用）。

## 六、需要你确认的点

1. **是否接受「扫描后/最小化到托盘时主动 trim 工作集」**？它让任务管理器里的内存数字立刻变好，但会把页换出，第一次点开面板时会有一次极短的卡顿（SSD 上通常 < 50 ms）。如果你更看重响应速度，可以只在扫描结束后 trim，不在隐藏时 trim。
2. **扫描时建议引擎要不要跳过 WinSxS 的精确测量**（P2-8，省 8 秒扫描时间，但 WinSxS 的数值改为取扫描聚合值，误差来自「深度 4 以下目录」）？
3. 是否顺带做 **P1-4 建议引擎改原生**（收益：句柄 −99%，代码量约 120 行，逻辑照抄 `Scanner`）。

> 附：本轮已按你的要求改掉「最小化到托盘弹气泡」（`WM_CLOSE` 现在静默隐藏），
> 并顺手修掉一个会导致**每次启动都重扫全盘**的调度 Bug（现在按「今天是否已有快照」判断）。

### 实际改动清单

| 文件 | 改动 |
|---|---|
| `Monitor.cs` | 新增 `ReleaseMemory()`（`Aggressive` 收集 + LOH 压缩，会 decommit 空闲段）；`TrimWorkingSet()` 提为公开且**只在扫描结束后由 UI 线程延迟 2 个心跳调用**（避免「刚 trim 就被重绘拉回来」）。`RefreshDerived(fresh:)` 复用内存里的新快照，不再从磁盘重载 3 份；去掉 `Baseline` 常驻；`History()` 改为返回轻量头 |
